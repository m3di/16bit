# Decisions

Decisions made before the build started. Each has a short reason. To change one, open an issue labelled `needs-human` and wait for the maintainer.

## Data model

| # | Decision | Reason |
|---|---|---|
| D1 | Postgres is the only required service and the single source of truth. | One thing to run, back up, and reason about. Caches and replicas are later performance work. |
| D2 | Hierarchy is workspace, hub, folder, item. A hub is a folder with no parent. | The hub is the unit of UI and of permissions. |
| D3 | Every folder and item stores its `hub_id`. | Isolation and permission checks become one indexed comparison, with no tree walk. |
| D4 | An item lives in exactly one folder. | One home per fact. Other placements are views or relations. |
| D5 | Item values are one JSONB column keyed by attribute ID. | A read is one row and a version check covers the whole item. Renaming an attribute costs nothing. |
| D6 | A derived `item_index` table holds typed copies of values for attributes marked "filter and sort". | Filtering and sorting stay indexed without creating an index per attribute. |
| D7 | Relations are stored in a `link` table. | Backlinks and clean deletes. This is also the graph. |
| D8 | Every item has an integer `version`. Writes send the expected version and get a conflict if it moved. | Prevents silent overwrites between people and agents. |
| D9 | An append-only `revision` log with a per-workspace sequence number records every write. | History, undo, the real-time feed, and audit come from one table. |
| D10 | Attributes belong to a hub, not the workspace. | A schema change in one hub cannot affect another. |
| D11 | Relations across hubs are off by default and enabled per attribute. | They are the one place data can leak between hubs. |
| D12 | Attribute types are a closed set of 13: text, rich text, number, boolean, date, select, multi-select, relation, actor, file, URL, auto ID, rollup. | The parser can refuse anything else. Email, phone, percent, and currency are formats, not types. |
| D13 | Changing an attribute's type is a migration job, never an in-place edit. | Old values must not silently stop validating. |

## Views

| # | Decision | Reason |
|---|---|---|
| D14 | A view is a tree of blocks with a registry that states which children each block allows. | Composition is flexible and can never loop. |
| D15 | Version 1 has 17 block types: page, section, columns, tabs; heading, text, divider, image; table, list, board, chart, number; fields, document, comments, activity. Amended in M4 (D77): M4 builds 11 of them; tabs, divider, image (needs file storage), document, comments and activity come later. | Enough to build real pages. More are added through the registry. The amendment keeps M4 to what the two mockups need. |
| D16 | Anything an agent should be able to query is an item, never view content. | The data API stays the whole truth. |
| D17 | A view is stored as one JSONB document with its own version, and blocks have stable IDs. Amended in M4 (D76): writes replace the whole tree with an expected version; patch by block ID is deferred. | One fetch, atomic validation, patch by block ID. Whole-tree writes are enough for one admin composing in settings. |
| D18 | Every block designs four states: loading, empty, error, no permission. A block or page that opens one thing by ID designs a fifth, not found. | Nothing on the presentation surface is ever undesigned. "Not found" was added after M2, when the item page and settings opened things by ID (the maintainer's answer to the M2 report). |

## API

| # | Decision | Reason |
|---|---|---|
| D19 | No GraphQL. One JSON query shape, the same filter tree that views use. | Query cost stays predictable and cacheable. |
| D20 | Queries are bounded: indexed attributes only, one level of relation expansion, a required limit, cursor paging. Any caller may also ask for a window by offset, up to 100,000, and for the total count (D61). | Every read maps to a known plan. |
| D21 | Read forms: describe, get, query, aggregate, view data, search, changes, digest. | Agents get ready-to-use shapes instead of assembling them. |
| D22 | The API is plain HTTP with JSON, mirrored as MCP tools. | Reaches nearly every model and framework. |
| D23 | Triggers are in scope (change feed and signed webhooks). An action or automation engine is not. | Agents are the "then that". |
| D24 | Triggers are evaluated from the log after commit, never inside the write. | Writes stay fast. |

## People, agents, and permissions

| # | Decision | Reason |
|---|---|---|
| D25 | People and agent keys are both principals and go through the same permission checks. | One model to secure. |
| D26 | Workspace roles: owner, admin, member, viewer, finance. Hub roles: hub admin, editor, commenter, viewer. | A workspace role sets what someone can do. Hub access sets where. |
| D27 | A hub grant is required to see anything in the hub. A folder grant can only narrow it. | Hubs are guarded against each other. |
| D28 | Agent keys are scoped to one hub and can never manage members or billing. | Limits the blast radius of a leaked or misled agent. |

## Stack and delivery

| # | Decision | Reason |
|---|---|---|
| D29 | TypeScript end to end, in a pnpm monorepo: `packages/core`, `apps/api`, `apps/web`. | Type contracts and the block registry run in both the browser and the server from one package. |
| D30 | Frontend: Vue 3, Vite, Tailwind, Material Symbols. | Maintainer's choice. |
| D31 | Backend: Node with a small HTTP framework, a typed SQL query builder, and schema validation shared with the frontend. | Dynamic filter queries need a builder, not an ORM. |
| D32 | Desktop first and fully responsive. No native mobile app for now. | Scope. |
| D33 | Trunk-based development. Deploy from `main`. | Short branches, always releasable. |
| D34 | One container image serves both the API and the built web app. Only backend pods scale. | Standard web app on Kubernetes. |
| D35 | CI runs lint, typecheck, unit tests, build, and end-to-end tests. Every major function has an end-to-end test. | A green pipeline means something. |
| D36 | Pull requests from forks never run on self-hosted runners. | That would execute a stranger's code inside the cluster. |

## Project

| # | Decision | Reason |
|---|---|---|
| D37 | Code is Apache 2.0. The name "16bit.info" and the logo are reserved. | Anyone may fork and sell under another name. Only the maintainer uses the name. |
| D38 | Public issues and pull requests are welcome. Only the maintainer merges contributions from outside the agent team. | Personal project with one owner. |
| D39 | Light theme first, with every colour a CSS variable so dark mode is a token swap. | Both themes from one design. |
| D40 | API routes are scoped by workspace in the path: `/v1/workspaces/:workspaceId/...`. | IDs are unique per workspace (keys lead with `workspace_id`), and the workspace is visible in links and logs. Decided during M0 (#6). |
| D41 | **Retired in M1 (#51).** Was, for M0 only: `DEV_ANONYMOUS_AS_OWNER=true` let API requests without an `Authorization` header act as the dev owner, so the dashboard served by the container image worked without a key in the browser, guarded to loopback hosts. Removed together with the M0 development key once people could sign in; every request now needs a session or an agent key. | The browser had no key in M0. Real auth (D42) replaced it. Approved by the maintainer (#13); retired as planned in M1. |
| D42 | People sign in with email and password, hashed with argon2id. Sessions are stored in Postgres and sent as an httpOnly cookie. Passwords are reset only by the installation operator through a CLI command; self-service reset waits for an email service. | No outside service (D1), simple to self-host, and no admin of one workspace can take over an account that also belongs to another. Decided for M1. |
| D43 | M1 is invite-only. Owners and admins add members or create one-time invites through the API. There is no public sign-up. | No abuse handling needed before there is a deployment. The UI comes with settings in M2. |
| D44 | M1 builds every attribute type except file and rollup (D12). Rich text is stored as a JSON document. File waits for a storage decision; rollup comes with aggregation (M4). Amended in M4: rollup is deferred past M4; aggregates (D80) don't need it. | Keeps M1 to access and query; the two heavy types need their own design. The M4 exit needs no rollup. |
| D45 | The role matrix is `docs/ROLES.md`. Hub grants bind owners and admins too: they may grant themselves access, recorded in the log, but see nothing inside a hub without a grant. Hidden resources return 404. | Hubs are guarded against everyone (D27), and leaked owner sessions don't expose every hub. |
| D46 | People have one installation-level `account` (email, password) and one `principal` per workspace. `account` and `session` sit outside row-level security. `/v1/auth/*` and `/v1/me` are the only routes besides `/health` not under a workspace (exception to D40). | One login for several workspaces. |
| D47 | Each agent key is its own principal of kind `agent`, workspace role `member`, with exactly one `hub_grant` (editor, commenter or viewer). The key row holds only the secret hash, expiry and revocation. Agents get no workspace actions. | Permission checks and row-level security treat agents and people the same way (D25, D28). |
| D48 | Access changes (grants, role changes, member removal, keys created or revoked, invites created or revoked) go to an append-only `access_log`, separate from the item `revision` log. | Self-grants by owners and admins stay visible without mixing access history into item history. |
| D49 | A request carrying both a session cookie and an `Authorization` header is refused with 400, whatever the header holds and whether or not the session is live. | Ambiguous credentials would let an agent key silently act with a person's rights, against D28, and would log writes under the wrong principal. Decided during M1 (#42). |
| D50 | Each hub names one of its `text` attributes as the item title (`title_attribute_id`, set only on hub rows). With none set, or an empty value, an item shows only its mono ID. Hub admins change it in hub settings. Removing the title attribute clears it. | Items need a title on the item page and in links without adding a column outside the attribute model. Replaces the M1 stopgap of "first text attribute by position". Decided for M2. |
| D51 | An attribute's type is fixed once created, and so are a relation's target hub and its cross-hub flag (D11). Its name and its select options can change, and so can whether a folder requires it (`folder_attribute.required`). Removing an option or an attribute that items use shows how many items are affected and needs confirmation. To change a type or target, add a new attribute. A folder may start requiring an attribute that existing items leave empty: settings shows how many, and those items stay valid. As today, an edit that does not touch the attribute succeeds, and a required value cannot be cleared once set. | No conversion rules per pair of types, no broken links, and no value silently dropped. Decided for M2 (#108). |
| D52 | A folder or hub can be deleted only when it holds no items and no folders. Deleting an empty hub revokes its agent keys (the key rows stay, revoked, as with any revocation), deletes every grant on it and its attributes, and logs the grant and key changes in `access_log`. It is refused while a relation attribute in another hub targets it. The owner or admin deleting it must hold a grant on it, and an admin is refused when an owner holds a grant on it (`docs/ROLES.md` footnote 1). One narrow `SECURITY DEFINER` function does the delete. The revision history of the hub's deleted items stays, readable by no one. | Nothing is lost in one click; deleting data stays an explicit act on items. Checking emptiness reads inside the hub, which needs a grant (D45). Decided for M2 (#108). |
| D53 | Editing root views waits for blocks in M4. M2 settings cover members, invites, hub access, agent keys, folders and attributes. | A view is a tree of blocks, which do not exist before M4. Decided for M2. |
| D54 | Folder grants that narrow a hub grant (D27) wait until after M2. Settings grant access per hub. | Folder grants need their own row-level security and UI; M2 stays on its exit criterion. Decided for M2 (#108). |
| D55 | Each hub has a schema lock: a transaction-scoped Postgres advisory lock keyed by workspace and hub (`apps/api/src/schema-lock.ts`). Item creates and patches take it shared, before they read the folder's attributes to validate. Removing select options or deleting an attribute takes it exclusive, before it locks the attribute row and strips values. Renames, new options and other schema writes don't take it, and neither do item deletes. While a removal runs, item creates and patches in that hub wait for it; shared holders never wait for each other, and other hubs are unaffected (a hash collision between two hubs only makes them wait). It costs one extra statement per item create or patch. | Without it, an item write that validated against the old options could commit a removed option, or a deleted attribute's value, after the strip. A row lock on `attribute` can't do this: under row-level security only hub admins may lock attribute rows. Decided by the maintainer for M2 (#112, PR #131). |
| D56 | A hub's ID prefix is unique in its workspace. Creating a hub with a prefix in use is a 409 `prefix_taken`. A deleted hub's prefix is free again, since nobody can read its history. Only owners and admins create hubs, and they already see every hub row, so the error tells them nothing new. | Two hubs showing `ENG-12` would make mono IDs ambiguous in links, comments and agent output. Decided for M3 (the maintainer's answer to the M2 report). |
| D57 | The change feed is one WebSocket per browser tab, `GET /v1/workspaces/:workspaceId/feed`, plus the same events over HTTP, `GET /v1/workspaces/:workspaceId/changes?after=&limit=`, for agents and for catching up. A client subscribes per hub, not per folder, and filters by folder itself. Everything the HTTP routes check happens before the upgrade and fails as a plain HTTP error: authentication, D49 (cookie and `Authorization` together), and the workspace (404). A cookie upgrade needs an `Origin` header whose host equals `Host`; an agent uses its key in `Authorization` and sends no cookie. Client messages are parsed with the `packages/core` schemas and capped at 4 KiB. Subscribing to a hub that is missing, hidden, or not the agent's own gives the same `not_found`, so a socket can't probe for hubs. | One connection carries every subscription, the HTTP route lets agents read changes without holding a socket (D21, D23), and the socket can't do anything a GET can't. |
| D58 | Feed events are read from `revision` under the subscriber's own identity, so row-level security decides what each socket sees, exactly as for a GET, and items are shaped by the same code as GET. An event carries the item as it is now (or that it is gone), not the patch; several revisions of one item in a batch collapse to the latest. Every `changes` message carries a high-water `seq`, even when everything up to it was hidden, so a client's `after` never stalls. Every read response that a client will keep live (item, query, hub) carries the workspace's `seq`, read with its rows in one `REPEATABLE READ` read-only transaction (inside the write transaction for a write's own response) so it is never newer than they are; a `changes` page or feed batch cut short by its limit reports its last returned `seq` as its high-water mark; the client subscribes with that `after`, applies an item only if its version is newer than the one it holds, and keeps a tombstone for each deleted ID. Each process keeps one dedicated `LISTEN` connection, coalesces notifications for 50 ms, and runs one read per subscriber. Past 1,000 missed changes the subscriber could see, the server answers `resync` and the client reloads what it shows. Schema writes and access changes also notify: a hub event makes clients reload the hub's schema, and a lost grant ends that hub's subscription. Sign-out, member removal, key revocation and a password reset notify too and close the affected sockets at once; the session or key is also checked every minute. Accepted: the workspace-wide `seq` and high-water mark show how much is written in hubs the caller cannot see, though never where or what; D45 hides hidden hubs everywhere else. | No second permission model to keep in step with RLS, and no gap between a first load and the feed. One read per subscriber per batch is fine for M3; fan-out at scale is M7's problem. |
| D59 | Every item write may carry a `clientMutationId` (a UUID), stored on its revision and unique per workspace and actor. A retry with the same ID applies nothing and answers as the first attempt did, with the item as it is now; the same ID with a different item or operation is a 422. The HTTP response confirms a write; the feed's echo of the ID only stops the client applying its own change twice. | Safe retries after a dropped connection, writes confirmed even while the socket is down, and no flicker when a client's own change comes back. |
| D60 | The web app keeps one normalised store per workspace, keyed by item ID, built on Vue's `shallowReactive` with frozen item objects that are replaced, never mutated. No state library. Views hold ordered windows of IDs. Optimistic writes sit in a pending layer above server state and are dropped on rejection, which shows the 409 conflict as today. There is no offline queue: a write while disconnected fails with a message. Dashboard hub counts refresh when the dashboard loads, not live. A field being edited keeps the reader's draft when a change arrives; the change is shown beside it ("Changed by <name> while you were editing", with the new value, announced to screen readers), and the save goes out with the version the draft was based on, so the usual 409 offers keeping theirs or the reader's own (decided by the maintainer during M3). | 50,000 deeply reactive items would be slow, and the store is small enough not to need Pinia. |
| D61 | Large folders render with `@tanstack/vue-virtual` and load in windows of 200 rows by offset, with the folder's total count sizing the scrollbar (`folder.item_count` when there is no filter). The query gains `order: "number"`, item number newest first, backed by its own index, and the folder table uses it by default, so an edit updates its row in place and a create or delete only shifts the window. With an attribute sort or a filter, a change to that attribute, a create or a delete refetches the visible window, debounced, keeping the selected row in view. Smooth means, for the default order: after a jump anywhere in a 50,000-item folder rows show within one second, scrolling has no main-thread task over 50 ms (measured with a `longtask` observer), and fewer than 100 rows are in the DOM; EXPLAIN tests prove the window is an index scan. Attribute sorts and filters on a 50,000-item folder still read the whole folder per window (D20, `docs/ARCHITECTURE.md`); M3 only bounds them at two seconds per window and leaves index-backed sorts to their own decision. | Cursor paging cannot jump to the middle of a scrollbar, and the M1 default order (last updated first) would move a row on every edit. An index scan with an offset of 50,000 costs tens of milliseconds, inside D20's bounds. |

## Agent coordination

Decided by the maintainer on 2026-11-21 with the first outside team: coding agents using 16bit as shared working memory, deployed unmodified behind a company login gateway. Details left open in the scope (field names, limits, response codes) are proposed in the issues and decided there by the maintainer.

| # | Decision | Reason |
|---|---|---|
| D62 | 16bit adds general primitives. "Agent working memory" is a layer on top: a hub template plus conventions, built by the outside team as a reference example in `examples/agent-memory`, which is reserved for them. Nothing specific to one use case goes into the core. | The core stays a general data structure (D16, D23); use cases compose it instead of bending it. |
| D63 | Every item write (create, patch, delete) may carry an optional cause: a short note, a list of evidence URLs, and an optional reference to the earlier change that caused it. It is stored on the revision and returned wherever revisions are read, including item history. Decided for M3. | Agents and people can say why a value changed and point to the proof, in the same log that already records who and when (D9). |
| D64 | An item may have one external key: optional opaque text, unique per hub, set on create or patch. Items can be read by key and upserted by key (create in a given folder, or patch the existing item), honouring `clientMutationId`. Without an expected version an upsert is last write wins on the fields it sends. The key is a built-in item field shown on the item page, not an attribute type (D12 stands). Detail (maintainer, #199): the field is `externalKey` (`item.external_key`, migration 0015), 1 to 200 characters, no control characters and no whitespace at either end, compared exactly; a patch with `null` clears it; a key another item of the hub holds is 409 `key_taken`. `GET` and `PUT /v1/workspaces/:w/hubs/:hubId/items/by-key/:key` (URL-encoded) read and upsert; the upsert answers 201 when it creates and 200 when it patches. `folderId` is used only on create: an upsert that finds the item in another folder patches it where it is, since items never move. | Clients that track their own identities (a file path, a ticket number) can write idempotently without first looking up 16bit's ID. |
| D65 | Batch writes: up to about 100 operations per call, each with its own mutation ID and its own result, so one failure does not fail the rest. Relation values in a batch may name items in the same hub by external key. Detail (maintainer, #199): `POST /v1/workspaces/:w/items/batch` with `{ operations }`, 1 to 100, each `{ op: "create" \| "patch" \| "delete" \| "upsert", ... }` in its route's shape; it answers 200 with `results` in the same order, each the status and item or error its route would give (a delete also gives its revision's `seq`, the first attempt's on a retry). Each operation runs in its own transaction, in order, so no transaction holds the workspace row for the whole batch. A relation value may name an item of the same hub as `{ "externalKey": "..." }`, including one created earlier in the batch. | Agents write many small facts at once without one round trip each, and keep per-operation retry safety (D59). |
| D66 | A patch or upsert may carry a precondition: a filter over the item's current values in the query operators (D19), evaluated with the server clock. If it fails nothing is written, and the answer is distinct from a version conflict. Writes can also set a date to the server clock plus an offset. Detail (maintainer, #199): `condition` takes the query `where` tree (D19), evaluated against the one item's current values, with every attribute allowed, not only indexed ones. A failed condition is 412 `precondition_failed` with the current item; a stale version stays 409 `conflict`. A date value or condition operand may be `{ "$now": "<ISO 8601 duration>" }` (for example `PT45M`, `-P1D`), evaluated with the database clock in the write's transaction, offsets capped at 366 days either way. Batches of 100 and keys of 200 characters are sized for D75. | Compare-and-set on values lets agents coordinate (claims, hand-offs) without trusting their own clocks or adding a lock concept to the schema. |
| D67 | Neighbours: a read form over the `link` table, also an MCP tool, in both directions, filtered by relation attribute, with depth capped at 2 and a capped node count. There is no unbounded traversal. | Agents need local graph context; bounded reads keep D20's promise. |
| D68 | Claim, renew and release are MCP tools only, sugar over D66 preconditions on two ordinary attributes the caller names (an actor and a date). The schema has no lease concept and the server runs no expiry job. | Coordination stays a convention over general primitives (D62). |
| D69 | A date attribute may have a "fresh for" duration. It adds an "is stale" filter evaluated with the server clock, a visible flag in the table and on the item page, and a marker in the digest. | Readers see which facts have gone stale without the server rewriting anything. |
| D70 | Basic search arrives in M5: a hub's title and text attributes, bounded and under row-level security. Search over rich text and comments stays in M6. | Agents need lookup by words before the full search lands. |
| D71 | Hub templates: export and import a hub's folders, attributes and views, without items. | A layer like D62's is shared as a template. |
| D72 | Trusted-header sign-in for deployment behind a login gateway. Off by default, enabled only with an allowlist of proxy addresses, and the header is ignored from anywhere else. 16bit stays invite-only (D43): the identity must map to an existing member, so members can be invited by an external login name as well as by email. Agent keys are unaffected. Every part of it is gated. | Teams deploy 16bit unmodified behind their company login without a second password. |
| D73 | M7 adds full hub export (items, links and history), backup and restore documentation, and OIDC sign-in. Webhooks stay as planned (D23). | Data can leave and be restored; deployments can use a standard identity provider. |
| D74 | Not doing: a built-in "fact" type or any other domain-specific item type; probes, curation or expiry jobs on the server; unbounded traversal; wildcard agent keys or keys spanning several hubs (deferred, so D28 and D47 stand); a tracker or code-host bridge inside 16bit; GitHub sign-in for now. | Each would put one use case into the core (D62) or widen an agent's reach. |
| D75 | Design target for this use case: a few hundred to 2,000 items per hub, 5 to 15 agents at once, tens of writes per minute, reads far outnumbering writes. | Limits and caps in D64 to D72 are sized for it. |

## Blocks

Decided by the maintainer on 2026-11-22 for M4 (`team/backlog-M4.md`, Q1 to Q9, PR #247).

| # | Decision | Reason |
|---|---|---|
| D76 | Each folder (the hub root included) has one root view or none; without one it opens on `page > table(this folder)`, or "No view yet" in a views-only folder. The `view` table holds `{ schemaVersion, root }` as JSONB, unique per folder, at most 128 KiB; `parseViewTree` upgrades old versions on read. Writes replace the whole tree with an expected version (409), reset is `DELETE ?version=`, no history, and a write sends the `hub` NOTIFY. A views-only folder (fixed at creation) holds no items, enforced by a trigger; the hub's folder row names the folder it opens on. Deleting a folder with a stored view is refused (409 `has_view`) until the view is reset; deleting a hub removes its views. Decided for M4. | One fetch and atomic validation (D17); the mockup's Home and My work are folders that only show views; nothing composed is lost in one click (D52). |
| D77 | Blocks are `{ id, type, config, children? }` with a `BLOCK_TYPES` registry in core (category, allowed children, Zod config, binding kind). M4 builds page, section, columns, heading, text, table, list, board, number, chart, fields. Caps: 200 blocks, depth 8, 20 data blocks. Rows and cards show up to 4 fields; list groups up to 2 measures; boards show an ordered subset of a select's options, empty columns included. Create works in the binding's folder and presets only top-level `AND` equality conditions. `$block` names only an item-bound block, never from an item rule; when it resolves to nothing, dependents show `unresolved`. Decided for M4. | The registry keeps the tree checkable in one place; the caps bound one page's cost. |
| D78 | Editing root views needs `hub.manageSchema` (hub admin); agents never edit views; reading needs `hub.read`. RLS on `view` mirrors `attribute`. Decided for M4. | The same people who shape the hub shape its views; no new action. |
| D79 | Set bindings follow `POST /query`'s rules in the view's own hub; item bindings are a fixed item or a first-match rule. New operands: `$me`, `$now` (defined by #199) and `$block` (views only). A block that names a removed or non-indexed attribute or a missing folder stays stored and renders "invalid"; PUT validates under the hub's schema lock shared. Every read runs as the caller under RLS in one snapshot with the workspace `seq`. Decided for M4. | Views read through the same bounded paths as the API (D20); one snapshot makes a page consistent. |
| D80 | `POST /v1/workspaces/:w/aggregate`: one group dimension (select, multi-select, actor, relation, boolean, or a date bucket), 1 to 5 measures from the type's summaries with their own `where`, at most 40 conditions in total, 100 groups and 366 date buckets. Actor groups return IDs only; hidden relation targets fold into one `no_access` group. Budget: 200 ms on a 2,000-item hub, 2 s on 50,000 items, 3 s statement timeout (503). Decided for M4. | Numbers and charts come from one bounded call; no group reveals a principal or item the reader can't see. |
| D81 | Dates in views use the reader's browser time zone, sent as `tz`; UTC when absent (agents); an unknown zone answers 422. Sprint days count weekdays (Monday to Friday, no holiday calendar); `number` and `chart` blocks can switch to calendar days. Decided for M4. | "Today" and the current sprint are the reader's; the mockup's "day 6 of 10" counts weekdays. |
| D82 | Where the mockups go past the data model: burndown from a "Done on" date, not history; Team open points grouped by Owner, no status line or Team folder; release bars over all epics, no release date; no subtask rollup on cards; no generated sentences or name tokens; the live dot is the connection state. Decided for M4. | Each needs a type or history M4 doesn't build (D44, D20). |
| D83 | `GET /v1/workspaces/:w/folders/:folderId/view/data?version=` answers every data block in one snapshot with a status each, at most 1,000 items, 409 `stale` when the tree moved, within one 5 s deadline. Up to 4 such requests in flight per principal per API process; the client retries a 429 silently. Blocks refetch on changes to their bound folder, `$block` folders and relation target folders, debounced and at most once a second per view, and at midnight when they use `$now`. Decided for M4. | One request per page; the limit guards the pool against D75's write rate without breaking two tabs. |
