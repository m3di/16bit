## What works

- **Root views (D76 to D83).** A folder has one view or none; with none it shows today's table, unchanged. Views-only folders, a hub's "Opens on" folder, and deleting a folder that has a view refused until it's reset. Hub admins edit views; agents never can.
- **Blocks.** Layout and content (page, section, columns, heading, text) and data (table, list, board, number, chart, fields). Lists and boards group with summaries and "New item" pre-filled from simple filters; the burndown is a hand-drawn SVG chart in weekdays. One broken block never breaks the page.
- **Data.** `POST /aggregate` (groups, measures, date buckets in the reader's time zone, people as IDs only, hidden items counted but never named) and `GET /folders/:id/view/data` (every block in one snapshot, per-block statuses, a 5 s deadline, at most 1,000 items, 4 requests in flight per person). `$me`, `$now` and `$block` in filters.
- **The composer** in hub settings: outline, a form per block type, filters as a list or JSON, live preview, save with a version check, reset.
- **Live updates.** Views reload only the blocks a change touches, at most once a second.
- **Agents.** External keys with get and upsert by key, write preconditions (412), server-clock dates, and `POST /items/batch` with up to 100 operations, each in its own transaction.
- **Speed.** The worst-case aggregate on the 50,000-item folder went from 1.5–2.2 s to 0.45–0.64 s on CI, through `hub_id` on `item_index` with a plain hub check in its access policy (#300) and one-pass grouping (#304). Sorted, filtered pages halved, closing #193.
- **UI changes you asked for:** the root folder's own count, folder menus in the sidebar, "Edit folder", a settings gear per hub on the dashboard, the theme as one moon/sun button, the items table filling the page, and the item panel scrolling on its own.
- **Fixes:** NUL characters answer 400 or 422 everywhere instead of 500; one unreadable history entry no longer breaks the whole history; a save in flight can no longer silently overwrite someone else's change (#269); paging on long text sort keys (D84).

## What the team would change about the workflow

- **Measure where it runs.** The aggregate measured 0.8 s on a laptop and 1.5–2.2 s on CI, and isolating it in its own CI step didn't change that. The real fixes were a simpler access check and fewer engine passes. A later 2,000-task budget failed only because a fresh database had no planner statistics. Budgets should be measured on CI from the start, and seeds should end with `ANALYZE`.
- **Stacked PRs work if the base merges first.** Several PRs were built on unmerged branches (the composer on the data blocks, the sidebar menus on the root count). It worked once each base merged and the next was brought up to date, but GitHub's "update branch" and squash merges made conflict churn. Keep stacks short.
- **Reviewers keep finding real bugs.** Among them: a hidden-folder probe through a database error code, a select-option cap broken by an optimisation, a view-data deadline that wasn't enforced per query, a preview showing stale data, and a draft save that could overwrite someone else's change. Each became a test that fails without the fix.
- **Agents sometimes stall or lose their report.** A usage limit paused everything once, and several agents could only report once and went silent after a second task. Giving each agent one task at a time, and checking the PR itself when an agent goes quiet, kept work moving.
- **Your laptop.** Heavy local runs overheated it. The light-runs rule is now in CLAUDE.md, the workflow and the QA brief.
