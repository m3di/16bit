# M1 report: data API and access

Written by the lead on 2026-11-17, at the end of Sprint 1 (#56).

## Summary

The M1 exit criterion is met. Two seeded people with different roles and one agent key are checked against every row of `docs/ROLES.md` that has a route in M1, in the API and in the browser. They see and can do exactly what the matrix says: 64 end-to-end tests, none skipped. The API enforces the matrix and Postgres row-level security enforces it again underneath. The dashboard requires sign-in, and D41's anonymous dev owner is gone.

All 16 planned issues are closed, along with 13 follow-ups, through 32 merged pull requests. Each was reviewed by the `reviewer` agent. Every gated change was merged only after the maintainer said yes in the conversation. `main` requires three checks: `Lint, typecheck, test, build`, `End-to-end` and `Container image`.

## What works

- **People:** people sign in with email and password (argon2id) and get a server-side session in an httpOnly cookie (D42). Accounts are installation-wide, with one principal per workspace (D46). Joining is by invite only (D43). Passwords are reset by the operator's CLI only, and the shared dev password is refused in production at sign-in, on invite and on reset.
- **Agents:** each agent key is its own principal with one hub grant (D47). Keys are shown once and stored hashed, and their role is capped at the creator's. A request that sends both a cookie and a key is refused (D49).
- **Roles:** workspace roles and hub grants follow `docs/ROLES.md`. Hidden things return 404 and forbidden things 403. Owners and admins also need a grant to see inside a hub (D45). Access changes go to `access_log` (D48).
- **Row-level security:** policies on every workspace-scoped table, plus guards against admin escalation, history forgery and the sequence counters being moved. The API connects as a role that cannot bypass RLS. It refuses to start as the owner, and never receives the owner database URL.
- **Data:** all attribute types except file and rollup (D44): multi-select, URL, actor, auto ID, rich text and relations. Relations use a `link` table with cross-hub links off by default (D11), one level of `expand`, backlinks that never name hidden items, and "no access" markers. Items can be filtered and sorted on indexed attributes through `item_index`.
- **Web:** sign-in, invite and sign-out flows. The hub list shows "no access" cards. Every new type has cells and editors, including a relation picker that only offers readable items. Column sorting has a visible cue, and the read-only state comes from the caller's hub role.

## How to run it

```sh
pnpm install
docker compose up -d db
pnpm seed           # demo workspaces, people, grants and one agent key
pnpm dev            # http://localhost:5173 — sign in as owner@example.com / 16bit-dev-password
```

The seeded people and their roles are listed in the README. Docker only: `docker compose up --build`, then `docker compose run --rm migrate node src/seed.ts --force`, and sign in on http://localhost:8080.

## Decisions the maintainer made during M1

- **D42–D49:** sign-in, invites, type scope, the role matrix, accounts, agent principals, the access log, and refusing a cookie sent together with an authorization header.
- **`docs/ROLES.md`:** two refinements. Key roles are capped at the creator's, and admins cannot touch owners' grants. Also: key revocation needs no grant, self-grants are API-only in M1, removing a member expires their unused invites, and backlinks only count hidden items.
- **Schema and API:** counter-free item index with list-valued projections; the filter semantics; stale relation IDs dropped on patch; workspace-scoped routes kept.
- **Design:** contrast token fixes; dashed no-permission marker; unboxed notices; the sort arrow before the label in right-aligned columns.

## Left out or deferred

- **Not built in M1:** file and rollup types (D44), folder grants (M2), billing, comments, renaming or deleting a workspace or hub, and schema management routes. Self-granting has no UI yet (M2 settings).
- **Known limits:**
  - An editor can write revisions with unusual version numbers for items in their own hub.
  - Sorting on an attribute costs O(folder size) per page.
  - The table sort isn't kept in the URL, and rows don't re-sort after an edit.
  - Inline chips cut off at a fixed count.
  - `DESIGN.md` still lists HubCard fields the API doesn't return (status line, last active).
- **M7 deployment notes (on #56):**
  - The login rate limiter is in memory and per IP.
  - The database owner must not be a superuser.
  - `revision_hub_fkey` needs a delete rule before hubs can be deleted.

## What the team would change about the workflow

- **Planning review paid off.** The first planning PR went through four review rounds and found real gaps: the account model, row-level security for sign-in, and the role matrix. It cost an afternoon and saved several rework rounds later.
- **Security work needs a hostile review.** Row-level security took four rounds. Each round found a real hole: admin escalation, key revocation, a leaking lock helper, forged revisions, and the owner URL in dev. Removing each restriction and checking that a test fails, done by both author and reviewer, was what made these reviews trustworthy.
- **End-to-end tests found a production bug.** The role-matrix suite exposed a deadlock between concurrent access changes. It was fixed with one documented lock order and forced-interleaving tests.
- **Parallel PRs collide on shared files.** Migration numbers, `packages/core/src/index.ts`, `ARCHITECTURE.md` and the lockfile collided often. When merging `main` into an approved branch is the only change left, the lead does it and gets a quick confirmation review (now in `docs/WORKFLOW.md`).
- **Relay messages to running agents need a second channel.** A message to an agent can sit unread. Constraints that matter now also go on the issue as a comment.
- **Shared scratch files caused one incident.** Two agents used the same script name, and one ran a command in the other's worktree. Scratch files are now named with the issue number (`CLAUDE.md`).
- **QA was often folded into the end-to-end suite.** Several user-visible PRs (#66, #72, #79, #80) merged as `qa:not-needed` because their end-to-end coverage was routed to #53, which landed later. That suite now exists, so in M2 QA should add or extend an end-to-end test inside each user-visible PR before it merges, as `docs/WORKFLOW.md` intends.
- **Cleanup must run per merged PR.** One cleanup step ran ahead of a merge and removed a worktree too early. Nothing was lost, but cleanup is now tied to each confirmed merge.
